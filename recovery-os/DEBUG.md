## Day 7 -- critical bug: idempotency key bound to the wrong identity
1. **Idempotency key used a surrogate database row ID instead of stable business identity.** execute.ts originally built the key as `intervention_${interventionId}`, where interventionId is an auto-increment row ID. Upstream, diagnoseBatch.ts and interveneOnBatch.ts had no guard against re-processing an event that was already diagnosed/actioned -- reruns silently inserted new diagnosis/intervention rows for the same events instead of skipping them. Each new intervention row got a fresh auto-increment ID, which meant a fresh idempotency key, which meant the idempotency check correctly saw "never seen this key" every time -- and dutifully executed a brand-new real Razorpay payment_links.create call. Result: 5 genuine duplicate payment links created in Razorpay test mode across repeated runs, before being caught.
   - No real money moved (test mode throughout), but this is exactly the failure class the whole idempotency design exists to prevent, and it happened because the key was keyed to *how many times we redid the work* rather than *what the work actually was*.
   - Fix (two layers): (1) execute.ts's idempotency key changed to `${eventId}_${finalAction}` -- stable business identity, immune to upstream duplication no matter how many times a row gets re-inserted. (2) diagnoseBatch.ts and interveneOnBatch.ts both got check-before-insert guards (skip if a diagnosis/intervention already exists for this event), fixing the actual source of duplicate rows rather than only patching the symptom at the execution layer.
   - Lesson for the README/pitch: an idempotency key must bind to the identity of the *work being done*, never to a database row ID that changes every time the work is accidentally redone. This is worth stating explicitly as a design principle, not just a bug fix -- it's the kind of mistake that's easy to make and expensive in a real production system.

## Day 9 -- first full end-to-end run surfaced two integration bugs, as expected
1. **Accuracy metric silently broke when skip-guards were added.** diagnoseBatch.ts's "correct" counter only incremented inside the per-event loop body, which is skipped entirely for already-diagnosed events (Day 7's guard). First full rerun showed "Accuracy: 0/10" even though all 10 diagnoses were still correct and untouched -- the metric just wasn't checking existing data. Fix: recompute accuracy from a fresh query against current stored diagnoses at the end of the run, independent of what happened to be freshly processed vs skipped in that specific invocation.
2. **psql couldn't display a stored message containing an emoji currency symbol.** SELECT on a conversations.messages row containing an already-correctly-stored rupee symbol (from Day 8) failed with a UTF8/WIN1252 encoding error -- purely a Windows console code-page display issue in this psql session, not a data problem (confirmed: Node/the app itself renders the same data correctly, per Day 8's test output). Fixed for viewing via SET client_encoding = 'UTF8' + jsonb_pretty(). Not a real bug, but worth remembering during the live demo: don't debug via raw psql output on Windows if something looks broken -- check via the actual application first.
- No other integration bugs surfaced -- diagnosis -> verification -> intervention -> policy gate -> execution -> conversational agent -> risk-flag lookup all worked correctly together on the first full run once the above two were caught.

## Track 3 P0 hardening — 2026-09-02
1. **Webhook endpoint trusted event IDs but not webhook authenticity.** The route previously parsed JSON globally and persisted whatever reached it. Fix: `/webhooks/razorpay` now captures the raw body, validates `X-Razorpay-Signature` with HMAC-SHA256 and `timingSafeEqual`, then parses/persists only after verification. Missing secret/signature fails closed.
2. **Event-time evidence leaked future failures.** Customer history had no timestamp cutoff and bank correlation used `ABS(...)`, so later events could influence an earlier diagnosis. Fix: both queries now end strictly before the event timestamp; bank evidence uses a 30-minute lookback only. Added `evidenceCutoffAt` to make the snapshot defensible.
3. **Policy safety context was hard-coded in the integrated batch path.** `0/false` prevented real stopping rules from ever firing. Fix: `loadPolicyContext()` reads automated retry attempts, actual outbound contacts in the last 24 hours, terminal recovery state, and opt-out state from Postgres/event state; the exact snapshot is included in audit entries.
4. **Agent-side payment-link generation bypassed the central gate.** The conversational tool directly called Razorpay. Fix: all payment-link side effects now go through `ActionService`; trusted amount/customer values are reloaded from the stored event and policy is re-run immediately before execution.
5. **SELECT-before-call idempotency was still concurrency-unsafe.** A UNIQUE key prevented duplicate rows but not duplicate external calls under two concurrent workers. Fix: `ActionService` first claims a `pending` action with `INSERT ... ON CONFLICT DO NOTHING RETURNING id`; only the claimant is allowed to call Razorpay.
6. **Outbound opening message was recorded as a customer/user turn.** `executeAction` called `runAgentTurn(opening)`, reversing message direction. Fix: `startOutboundRecoveryMessage()` stores the opening as `assistant`; `runAgentTurn()` is now explicitly inbound-only.
7. **Action success was incorrectly used as revenue recovery.** Fix: introduced one `recovery_cases` row per original failed event. A generated link moves the case to `WAITING_FOR_OUTCOME`; only a trusted `payment_link.paid` webhook can transition it to `RECOVERED` and record recovered amount. Evaluation now reports confirmed recovered ₹ separately from execution reliability.
8. **Webhook ingestion stopped at persistence.** Fix: `payment.failed` creates a durable `recovery_jobs` row and kicks `processRecoveryCase()`, which runs evidence -> diagnosis -> verifier -> action selection -> policy -> execution and persists stage state. Server startup also drains pending/failed jobs so persisted work survives a process restart.
9. **Known verification limitation of this connector-driven patch.** GitHub file mutations and static cross-file review were possible here, but no local Postgres/Razorpay/Groq environment is attached to the connector, so the end-to-end runtime test matrix has not been executed from this session. The PR must not claim tests passed until run locally/CI with the required services and secrets.
10. **P1 debt deliberately remains visible.** `retry_with_backoff` is still immediate rather than a real delayed scheduler; 429 transient retry/jitter, DB-level audit tamper resistance, full runtime schema validation, and durable human escalation work items remain follow-up tasks rather than being disguised as completed P0 work.
